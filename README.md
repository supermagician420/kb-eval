# kb-eval

一个只依赖标准库的确定性评测器：把「知识库问答回答得对不对」拆成可复现的数字，而不是靠人一条条读。

## 为什么做这个

另一个项目 `enterprise-kb-qa-agent` 里，模型可以生成很流畅的答案。但流畅不等于正确：它可能漏掉关键条件、引用错段落、在知识库没有答案时硬编，或者反过来什么都不敢答。

人工逐条看，既慢又不可复现。这个工具用 JSONL 存放测试用例，计算四个简单指标，并输出一份 Markdown 报告。

它不是「LLM 裁判」，也不假装能判断语义正确性。它只检查那些可以明确断言的东西：

- 该引用的段落，引用了吗？
- 引用里有没有无关段落？
- 答案里有没有必须出现的关键事实？
- 不可回答的问题，是否明确拒答？
- 可回答的问题，是否没有误拒答？

## 快速开始

要求 Python 3.8+，不需要安装第三方包。

```bash
python kb_eval.py --cases cases.jsonl --out report.md
```

当前样例结果：

```text
wrote report.md: 8/8 passed (100.0%)
```

跑测试：

```bash
python -m unittest -v
```

当前有 15 个测试，覆盖指标计算、拒答识别、JSONL 校验、报告生成和退出码。

## 指标

| 指标 | 计算方式 | 说明 |
| --- | --- | --- |
| Source recall | 命中的期望来源 / 期望来源总数 | 答案是否覆盖了该引用的知识 |
| Citation precision | 命中的期望来源 / 实际引用来源总数 | 引用里有多少是相关的 |
| Keyword coverage | 答案中出现的关键词 / 期望关键词总数 | 关键事实是否被表达出来 |
| Refusal accuracy | 拒答行为与 answerable 是否一致 | 不可答要拒答，可答不能误拒答 |

一个可回答用例通过，需要同时满足：

- 没有误拒答；
- Source recall = 100%；
- Keyword coverage ≥ `--keyword-threshold`，默认 60%。

一个不可回答用例通过，只需要拒答行为正确。此时召回、引用精确率、关键词覆盖率不适用，报告里显示 `n/a`。

退出码：

- `0`：全部通过；
- `1`：有失败用例（适合直接接 CI）；
- `2`：数据文件或输出文件有问题。

## 数据格式

每行一个 JSON 对象：

```json
{
  "id": "leave-sick",
  "question": "病假需要提前几天申请？",
  "answer": "病假建议提前 1 个工作日申请；突发情况可先告知直属主管，返岗后补交病假证明。",
  "cited_sources": ["HR-LEAVE-01"],
  "expected_sources": ["HR-LEAVE-01"],
  "expected_keywords": ["1 个工作日", "直属主管", "病假证明"],
  "answerable": true,
  "notes": "病假流程"
}
```

字段说明：

- `id`：唯一标识，重复会报错；
- `question`、`answer`：必填非空字符串；
- `cited_sources`：答案实际引用/检索到的来源，默认空数组；
- `expected_sources`：期望来源；`answerable: true` 时至少一个；
- `expected_keywords`：答案中必须出现的关键事实，默认空数组；
- `answerable`：默认 `true`；为 `false` 时表示知识库中无答案；
- `notes`：可选备注。

加载时会校验 JSON 语法、必填字段、类型、重复 ID，并在错误信息里给出行号。

## 报告

样例报告见 [report.md](report.md)。它会包含：

- 总体指标；
- 每个用例的 PASS/FAIL 与四项指标；
- 失败用例的答案、期望/实际来源、缺失来源、缺失关键词、拒答期望与实际。

## 测试设计

`test_kb_eval.py` 不只测「函数能跑」，还测边界：

- 完美答案通过；
- 少一个关键词时 coverage = 0.5 并失败；
- 引用错来源时 recall / precision 都为 0；
- 不可回答时拒答通过，硬答失败；
- 可回答却拒答时失败；
- `没有硬性规定` 这种正常否定不会被误判成拒答；
- 汇总时，不可回答用例不参与检索指标平均；
- 非法 JSON 的行号正确；
- 重复 ID、缺少期望来源会报错；
- 报告包含失败详情；
- CLI 失败时返回 1，数据缺失时返回 2。

## 已知局限

- 关键词匹配很笨：同义表达、语序变化、否定语境都可能误判。
- 来源标签必须一致，不能自动判断两个来源是否语义相同。
- 不评估答案是否「自然」，也不做事实性核查。
- 样例只有 8 条，适合演示流程，不足以证明系统整体质量。
- 不是 LLM-as-judge；没有模型调用，所以结果稳定，但也只覆盖可明确断言的部分。

## 和另外两个项目的关系

- `enterprise-kb-qa-agent`：故意保留缺陷的问答靶子，用来暴露问题；
- `llm-api-resilience-lab`：把 API 失败处理拆出来，单独修一个问题；
- `kb-eval`：把「回答质量」变成可重复的检查，避免只凭感觉判断。

三个项目都是实际写出来、跑过测试的代码，不是包装出来的项目名。
